## Почему так

### `astro_core/` — расчётное ядро, отдельно от `app/`

Ядро не импортирует ничего из `app` (ни FastAPI, ни базу, ни VK). Вход — дата/время/координаты/tz, выход — dict «астропаспорта». Это прямое следствие требования из CLAUDE.md: **ядро платформо-независимое**. Такое разделение даёт три вещи:

- ядро без изменений переиспользует Telegram-бот и любой будущий фронт;
- golden-тесты (сверка с astro-seek) гоняются без поднятия FastAPI и базы;
- расчёт можно будет вынести в отдельный сервис/пакет, если понадобится, без переписывания.

Файлы:
- **natal.py** — pyswisseph + kerykeion: планеты, дома (Placidus), аспекты с орбисами
- **wheel.py** — обёртка над kerykeion для SVG-колеса
- **matrix.py** — Матрица Судьбы, чистая арифметика по дате рождения
- **eastern.py** — восточный гороскоп (cnlunar/lunardate)
- **geo.py** — геокодинг (GeoNames) + timezonefinder; **историческую таймзону считать по координатам И дате рождения** — частая ошибка конкурентов, отдельно оговорено в CLAUDE.md
- **passport.py** — сборка единого JSON «астропаспорта» из результатов natal/matrix/eastern — этот JSON идёт и в LLM, и на фронт, и хранится в `charts.calc`

### `app/` — веб-слой

**Роутеры (`api/`) тонкие**, вся логика — в `services/`. Ручек всего шесть (см. план проекта), но, например, в `reports` уже сходятся кеш по (расчёт, тип, prompt_version), лимит бесплатных генераций на пользователя, статусы генерации и связь с оплатой — этому нужен отдельный модуль, а не код в роутере.

- **api/auth.py** → `POST /api/auth/vk`
- **api/charts.py** → `POST /api/charts`, `GET /api/charts/{id}`
- **api/reports.py** → `POST /api/reports/{type}`
- **api/orders.py** → `POST /api/orders`
- **api/webhooks.py** → `POST /api/webhooks/yookassa`

**services/**
- **auth.py** — проверка HMAC-SHA256 `sign` из launch params VK → выдача JWT
- **users.py** — `get_or_create` по паре `(platform, external_id)`
- **charts.py** — геокодинг → вызов astro_core → сохранение `calc` JSONB
- **reports.py** — кеш отчётов, лимит бесплатных генераций, статусы (`pending/ready/failed`), вызов LLM
- **orders.py** — создание платежа в ЮKassa, обработка вебхука → разблокировка отчёта
- **events.py** — запись событий воронки в таблицу `events`

**models.py** — все 5 таблиц (`users`, `charts`, `reports`, `orders`, `events`) одним файлом: на MVP пять таблиц не заслуживают отдельного пакета, разрежем на модули, когда станет тесно.

**llm/**
- **client.py** — клиент DeepSeek
- **prompts/** — промпт на тип отчёта, **Python-модулем, а не `.md`-файлом**: кроме текста нужен код, который рендерит расчёт в компактные строки для модели (`build_user()`), а у полного разбора ещё и `parse()` ответа по секциям. Контракт модуля — `VERSION`, `SYSTEM`, `build_user()`; `VERSION` бампается руками при любой правке текста. Кеш-ключ отчёта = (chart_id, type, prompt_version), уникальный индекс в базе даёт кеширование «бесплатно», через `SELECT` перед генерацией

### `app/web/` — стенд обкатки, а не фронт (решение 2026-07-27)

Параллельно с `api/` (JSON для Mini App) заводится `web/` — тот же FastAPI,
но отдающий готовый HTML через Jinja2. Это не сайт и не фронт: это
инструмент, которым промпты вычитывают перед тем, как показывать тексты
живым людям. Обоснование, почему обкатка идёт в вебе, а не в боте —
в [astro-context.md](astro-context.md), «Порядок выхода на платформы»;
коротко: в боте нельзя положить два разбора рядом, а именно сравнение
текстов ловит главную болезнь LLM-астрологии — «всем одно и то же».

Почему Jinja2, а не Vue: у стенда нет ни одного требования, ради которого
берут сборку. Ни npm, ни node_modules, ни `vite build` — правка шаблона
видна по F5. Настоящий фронт (VK Mini App на Vue) появится позже и от этого
кода не зависит.

Почему `web/` — отдельный пакет, а не роутеры в `api/`: у них разный
контракт. `api/` возвращает JSON и авторизует по JWT из VK-подписи;
`web/` возвращает HTML и узнаёт человека по cookie. Общее у них — только
`services/*`, которые оба зовут одинаково, и это ровно та граница, которая
описана в CLAUDE.md.

Три вещи, которые в HTML-слое решаются иначе, чем в API:

- **долгая генерация без JS.** DeepSeek отвечает 30–60 секунд; обычная форма
  висит белым экраном, человек жмёт «обновить» и запускает вторую генерацию.
  Поэтому `POST /chart` не ждёт LLM, а сразу редиректит на `/r/<token>`, и
  страница обновляет себя через `<meta http-equiv="refresh">`, пока текст не
  готов;
- **публичный адрес — токен, а не id.** `charts.token` (24 случайных байта):
  по последовательному номеру подставляется соседний и читается чужая дата
  рождения;
- **`/admin` под HTTP Basic Auth**: логин и пароль из `.env`, иначе таблица
  с персональными данными тестеров открыта интернету. Охрана висит на
  `APIRouter` целиком (`dependencies=[Depends(require_admin)]`), а не на
  отдельных хендлерах — новый маршрут защищён по факту появления.

Админка **только на чтение** (решение 2026-08-01). Редактирование `SYSTEM`
прямо со страницы обсуждалось и отклонено: правки жили бы в базе, а не в
git, где им место (история, ревью, воспроизводимый деплой), и потребовали
бы вычисляемой версии промпта — иначе кеш `(chart_id, type,
prompt_version)` молча отдал бы старый текст под новой редакцией. Промпты
правятся в `llm/prompts/*.py`, `VERSION` бампается руками; расхождение
видно в сводке по версиям на `/admin`.

Единица работы админки — **отчёт, а не карта**: у одной карты уже два
текста (`free_natal` + `full_natal`), после бампа `VERSION` появится
третий, и сравнивают именно тексты. Поэтому `?ids=` — это id отчётов, а
оценки из `events` джойнятся по `props->>'report_id'`: после смены версии
старые звёзды не должны переезжать на новый разбор.

### Генерация платных отчётов — без очереди

DeepSeek на полном разборе думает десятки секунд — держать HTTP-запрос столько нельзя, особенно в вебхуке ЮKassa (должен отвечать быстро). На MVP: `BackgroundTasks` FastAPI + поле `status` в `reports`, фронт поллит `GET /api/reports/{id}`. Очередь (arq/Celery + Redis) — отложена до v1.1, когда появятся рассылки по расписанию из плана месяца 2.

### tests/golden/

Эталонные даты для сверки с astro-seek (10 карт) — обязательный тест **до написания любого другого кода**, согласно жёстким ограничениям в CLAUDE.md. Ошибка в домах убивает доверие мгновенно.

## Бывшие открытые вопросы — как решились

- **GeoNames**: ни Postgres, ни SQLite. Победил простой текстовый файл
  `backend/data/cities.txt` (4.8 МБ, лежит в git), который целиком грузится
  в память процесса; поиск — `bisect` по отсортированному индексу
  нормализованных имён. Причина: справочник неизменяемый и маленький, а
  так он не требует ни таблицы, ни миграции, ни живого соединения — тесты
  геокодинга гоняются без базы вообще.
- **sync vs async SQLAlchemy**: async (asyncpg), как и предполагалось.
- **CPU-bound расчёт**: прежняя оценка «расчёт занимает миллисекунды,
  `run_in_executor` не обязателен» **оказалась неверной**. Реальный
  `compute_natal` — 50–150 мс Swiss Ephemeris, и всё это время
  однопоточный event loop не обслуживает никого. В `services/charts.py`
  расчёт уходит в `asyncio.to_thread`.
- **alembic**: настроен, `env.py` работает в async-режиме и берёт
  `DATABASE_URL` из настроек приложения (в `alembic.ini` адреса нет —
  пароль в git это утечка). Первая миграция создаёт все пять таблиц.
