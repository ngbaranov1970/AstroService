## Статус: смена курса — обкатка идёт в вебе, бот отложен

**Решение 2026-07-27:** промпты обкатываются на веб-стенде (Jinja2, две
страницы и админка), а не в Telegram-боте; бот едет следующим шагом.
Причина в одну строку: в боте нельзя положить два разбора рядом, а
сравнение текстов двух людей — главный тест качества промпта. Полное
обоснование — в [astro-context.md](astro-context.md), раздел «Порядок
выхода на платформы».

Что это меняет в работе: шаги «миграция №2 с `horoscopes`»,
`services/horoscopes.py` и пересадка бота **отложены** — они про рассылки
по знакам, то есть про старую функциональность бота, и к тестированию
промптов отношения не имеют. Шаги `services/charts.py` и
`services/reports.py` нужны при любом сценарии и делаются как
запланировано. Из `services/users.py` пока нужен только `get_or_create`.

### Ранее: БД мигрирует, монорепо связано в workspace, бот переехал в `/bot`

Схема БД живёт в коде и накатывается Alembic'ом: цикл `upgrade head` →
`downgrade base` → `upgrade head` пройден целиком, `alembic check` после наката
не видит расхождений между моделями и базой.

Существующий Telegram-бот (BotHoroscope) скопирован в `/bot` и подключён к
backend через uv workspace: `import app.services` из бота работает. Сам бот
сейчас НЕ ЗАПУСКАЕТСЯ — из него удалён слой доступа к SQLite, а замена
(`app/services/*`) ещё не написана. Это и есть текущая работа.

Жёсткое требование CLAUDE.md — **сверка 10 эталонных дат с astro-seek до
написания любого другого кода — выполнено**: 10 карт, все сошлись в пределах
минуты дуги (планеты, Асцендент, MC, куспиды Placidus, дома, ретроградность).

## Что сделано

### Реализованные модули

| Файл | Что делает |
|---|---|
| `backend/astro_core/geo.py` | Офлайн-геокодинг: ~70 тыс. городов GeoNames в памяти, префиксный поиск по русским (включая исторические — «Свердловск» → Екатеринбург) и латинским именам через bisect; таймзона города из базы, для произвольных координат — timezonefinder. Возвращает всегда ИМЯ зоны IANA, смещение по дате достаёт tzdata в расчётном слое. |
| `backend/astro_core/natal.py` | Натальная карта на kerykeion 5 (`AstrologicalSubjectFactory` / `AspectsFactory` — новый API, мигрировано со старого): планеты, углы, дома Placidus, аспекты. Чистая функция `compute_natal(birth_dt, lat, lon, tz) → dict`, про geo/FastAPI/БД не знает. |
| `backend/scripts/build_cities.py` | Однократная сборка `backend/data/cities.txt` из GeoNames (cities5000 + русские имена из alternateNamesV2 по метке `isolanguage=ru`). |
| `backend/scripts/natal_cli.py` | Ручная проверка: `python scripts/natal_cli.py 1990-05-11 17:20 Касимов` печатает карту в формате astro-seek (градусы°минуты'); флаг `--json` пишет эталон для tests/golden/. |
| `backend/scripts/seek_check.py` | Автосверка с astro-seek: качает их расчёт по тем же координатам (таймзону astro-seek определяет сам — независимая проверка нашей цепочки), парсит HTML и сравнивает с `compute_natal`. Калиброван на картах, проверенных глазами. |
| `backend/tests/test_natal.py` | Золотые тесты: пересчитывают каждую карту из `tests/golden/*.json` и сравнивают (знак/дом/ретро точно, градусы с допуском 0.01°). Ловят регрессии при обновлении kerykeion/pyswisseph/tzdata. |
| `backend/app/llm/client.py` | Транспорт к DeepSeek (httpx, без SDK): один вызов `chat(system, user)`, ретрай на 429/5xx, расход токенов в `LLMResult.usage`. Модель по умолчанию `deepseek-v4-flash`; temperature 1.0 — откалибровано (1.3 разваливает текст v4-flash в бессвязицу). |
| `backend/app/llm/prompts/free_natal.py` | Промпт бесплатного разбора (`free_summary`): `VERSION` для ключа кеша отчётов, стабильный `SYSTEM` (тон + запреты для модерации VK, у DeepSeek кешируется — 1024/1058 ток. из кеша на втором вызове), `build_user()` рендерит dict из `compute_natal` в компактный текст (10 самых тесных аспектов). |
| `backend/scripts/report_cli.py` | Сквозной прогон в терминале: дата + город → geo → natal → промпт → DeepSeek → текст. Флаги `--show-prompt` (без трат токенов), `--temperature`/`--model` для калибровки. |
| `backend/app/config.py` | Настройки через pydantic-settings. Описаны только реально используемые переменные (`DEEPSEEK_API_KEY`, `DATABASE_URL`, `DB_ECHO`, `APP_ENV`, `DEBUG`); ключ — `SecretStr`, чтения ленивые через `get_settings()`, иначе любой импорт требует заполненного `.env` — включая pytest и alembic. |
| `backend/app/models.py` | Все пять таблиц схемы: `users` (пара platform+external_id, is_tester, доставляемость рассылок, мягкое удаление), `charts` (локальное время рождения + tz, `calc` JSONB, `input_hash` против дублей), `reports` (ключ кеша `chart_id+type+prompt_version`, корпус: текст, модель, temperature, usage), `orders` (публичный `token` для ссылки оплаты, копейки целым числом, `provider_payment_id` UNIQUE против двойного зачисления вебхуком), `events` (воронка: name + props JSONB + ts). Enum'ы — varchar+CHECK, не нативные PG-типы. |
| `backend/app/llm/prompts/full_natal.py` | Промпт платного полного разбора (`full_natal_v2`, второе поколение — см. [astro-prompts-v2.md](astro-prompts-v2.md)). Ставка не на мягкость тона, а на конкретность: модель обязана называть элемент карты за каждым тезисом. Свой `TEMPERATURE = 0.8` (ниже общего 1.0: выше — теряется привязка к данным карты, ниже — канцелярит). Ответ модели — JSON по секциям, не сплошной текст: пейволл открывает первую секцию и закрывает остальные, а разрезать сплошной текст по границам смысла нельзя. `build_user()` отдаёт карту целиком (все дома, больше аспектов), `render()` собирает JSON обратно в читаемый текст для вычитки. |
| `backend/app/db.py` | Инфраструктура Postgres без единой таблицы: `Base`, ленивые `get_engine`/`get_sessionmaker`, зависимость `get_session` (транзакцией управляет вызывающий), `dispose_engine`. Асинхронный стек SQLAlchemy 2 + asyncpg — обработчик всё равно ждёт DeepSeek десятки секунд. Заданы `expire_on_commit=False`, `pool_pre_ping=True` и соглашение об именах ограничений (обязательно **до** первой миграции). |
| `backend/app/services/charts.py` | Продуктовая склейка «данные рождения → строка в `charts`». `search_places()` (подсказки городов, синхронно, справочник в памяти) и `create_chart()` — намеренно ДВА вызова: между ними человек выбирает, какой из Ростовов его. Дубли ловятся не сравнением полей, а хешем входа (`_input_hash`, sha256; координаты округляются до 4 знаков, иначе последний бит float даёт «разные» города) плюс уникальная пара `(user_id, input_hash)` в базе. Расчёт уходит в `asyncio.to_thread`: 50–150 мс Swiss Ephemeris в event loop заморозили бы весь процесс. Вставка под `begin_nested()` (SAVEPOINT) — на гонке двух одинаковых отправок формы возвращаем ту карту, которую успел записать конкурент, вместо «current transaction is aborted». **Тестов пока нет.** |
| `backend/app/services/users.py` | Одна функция `get_or_create()` по паре `(platform, external_id)`: веб-стенд зовёт её с `platform='web'` и UUID из cookie, бот позже — с `'tg'` и Telegram-id. Три шага: SELECT (быстрый путь, по нему идёт большинство запросов) → `INSERT … ON CONFLICT DO NOTHING RETURNING` (вставку и разрешение гонки делает сама база одной командой) → повторный SELECT, если пустой RETURNING показал, что конкурент опередил. `source` проставляется только при создании — канал привлечения это свойство первого касания. Вернувшемуся снимается `deleted_at`: строка для того и оставлена, чтобы он не упёрся в конфликт по уникальной паре. Коммита нет, транзакцией правит вызывающий. |
| `backend/alembic/` (`env.py`, `versions/a316a204b535_init_tables.py`) | Миграции. `env.py` работает в async-режиме (движок тот же asyncpg, что у приложения) и обязательно импортирует `app.models` — без этого импорта `Base.metadata` пуста и autogenerate решил бы, что все таблицы надо удалить. Адрес базы в `alembic.ini` намеренно не записан (пароль в git — утечка): `env.py` берёт `DATABASE_URL` из настроек приложения, поэтому alembic и приложение не могут разъехаться по базам. Первая миграция создаёт все пять таблиц. |

### Переезд Telegram-бота (2026-07-26)

Старый бот жил отдельным проектом (`~/VScode Projects/BotHoroscope`,
aiogram + aiosqlite + Redis + APScheduler). Скопирован в `/bot` без `.git`,
`.venv`, `bot.db`, `.env` и старого `CLAUDE.md`. Внутренняя папка `bot/bot/`
переименована в `bot/tg/` — двойная вложенность делала импорты нечитаемыми.

**Базу подписчиков НЕ переносим.** В `bot.db` на момент переезда было
2 пользователя, на проде — несколько десятков, «все свои». Вместо скрипта
миграции: старый бот рассылает сообщение со ссылкой на новый, люди жмут
`/start` заново и попадают в `users` с `source='bot_old_base'`. Порядок
важен — рассылку делает СТАРЫЙ бот, потому что новый не имеет права писать
первым тому, кто с ним не заговорил. После рассылки старый бот не гасим,
а подменяем ему код на заглушку со ссылкой; глушим совсем через месяц-два.

У нового бота **свой токен и своё имя**: два процесса с одним токеном
несовместимы (Telegram роняет второго с `Conflict: terminated by other
getUpdates`), поэтому пока старый бот жив на проде, в `bot/.env` стоит токен
тестового бота. Переключение в конце — замена токена, не «миграция».

| Файл | Судьба |
|---|---|
| `bot/tg/{handlers,keyboards,texts}.py` | остаются в боте: всё, что знает про Telegram |
| `bot/services/broadcast.py` | остаётся: отправка сообщений — транспорт |
| `bot/main.py`, `bot/config.py` | правятся: DI и планировщик хорошие, зависимости меняются |
| `bot/db/repo.py` | **удалён** — сырой SQL к SQLite, замена `app/services/*` |
| `bot/services/llm.py` | под удаление — есть `app/llm/client.py` |
| `bot/services/horoscope.py` | переезжает в `app/services/horoscopes.py` |
| `Dockerfile`, `docker-compose.yml`, `deploy/` | устарели (pip, SQLite-volume, Redis), переделываются на шаге деплоя |

Граница, по которой делится код: **`bot/` знает про Telegram, `app/services/`
знает про наши данные, пересечения нет.** Поэтому гороскопы по знакам ушли
в `app/services/` (они пишут в нашу таблицу и ходят в наш LLM-клиент), а
рассылка осталась в боте (это отправка сообщений). Из того же правила следует
запрет: в `app/services/*` не должно быть ни одного объекта aiogram — иначе
код станет непригоден для Mini App, который будет ходить в те же сервисы
через `app/api/*`.

Мелочь для будущего переноса: `bot/services/horoscope.py` тянет `SIGNS` из
`tg/texts.py`. При переезде вниз коды знаков надо отделить от их отображения
(названия и эмодзи остаются в боте).

### Монорепо: uv workspace (2026-07-26)

Корневой `pyproject.toml` не описывает пакет — он объявляет workspace из
`backend` и `bot`. `astro-backend = { workspace = true }` в `bot/pyproject.toml`
ставит backend в editable-режиме, поэтому `import app` работает из бота без
фокусов с `sys.path`. Следствия: окружение и `uv.lock` теперь ОДНИ на весь
репозиторий и лежат в корне (`backend/.venv` и `backend/uv.lock` удалены —
в VS Code нужен интерпретатор `AstroService/.venv/bin/python`); версии
общих пакетов у бота и backend физически не могут разъехаться.

Из зависимостей бота выброшены `aiosqlite` (заменён Postgres), `redis`
(кешировать поверх Postgres десяток строк незачем — минус контейнер, volume
и ветка «а если недоступен» в коде) и `openai` (свой клиент на httpx).

### Зафиксированные решения

- **Узел**: считаем истинный (true node); astro-seek в основной таблице
  показывает средний — расхождение до ~1.5° это норма, не баг.
- **Lilith, Fortune, Vertex** не считаем (пока не нужны продукту).
- **Аспекты** с astro-seek не сверяем — у них другие орбы по умолчанию,
  списки законно различаются.
- **Округление**: мы округляем минуты дуги, astro-seek усекает — наши минуты
  систематически на +1' больше, реальная разница — доли минуты.
- `cities.txt` коммитим в git (4.8 МБ, нужен для работы и тестов);
  исходные zip GeoNames и кеш astro-seek — в .gitignore.

## Как запустить

Окружение одно на весь репозиторий; команды запускаются из папки своего
проекта, uv сам находит корень workspace вверх по дереву.

```bash
# из корня репозитория: поставить зависимости обоих проектов
uv sync --all-packages --extra dev

cd backend

# если backend/data/cities.txt отсутствует:
uv run python scripts/build_cities.py

# тесты (11 шт: 10 золотых карт + защита от пустого каталога):
uv run --extra dev pytest

# база: накатить схему (нужен работающий Postgres и заполненный .env)
uv run alembic upgrade head

# сверить модели с базой — молчаливое "No new upgrade operations detected"
# означает, что код и база совпали; любой вывод операций = забыли миграцию
uv run alembic check

# новая миграция после правки app/models.py (файл потом ВЫЧИТАТЬ руками —
# autogenerate не видит переименований и хуже всего справляется с данными):
uv run alembic revision --autogenerate -m "что изменили"

# посчитать карту руками:
uv run python scripts/natal_cli.py 1990-05-11 17:20 Касимов

# сверить дату с astro-seek и записать новый эталон:
uv run python scripts/seek_check.py 1993-02-01 12:00 Пермь
uv run python scripts/natal_cli.py 1993-02-01 12:00 Пермь --json > tests/golden/1993-02-01_perm.json
```

## Решения по стратегии

Обкатка идёт **сначала на веб-стенде**, потом бот, потом Mini App (решение
2026-07-27, заменяет порядок от 2026-07-25); подробности и обоснование — в
[astro-context.md](astro-context.md), раздел «Порядок выхода на платформы».
Следствия для кода, которые надо держать в голове:

- в `users` — пара `(platform, external_id)` вместо `vk_id`, плюс `is_tester`
  (тестерам открыт полный разбор без оплаты). Веб-пользователь — это
  `platform='web'` и случайный UUID в cookie: пара для того и заведена;
- **все генерации логируются** (текст, `prompt_version`, модель, temperature,
  usage) — из этого корпуса потом строится пост-фильтр текста, без которого
  на модерацию VK идти нельзя;
- веб-стенд дёргает `app/services/*` напрямую, теми же вызовами, что позже
  будет дёргать бот. `app/api/*` (JSON для Mini App) не трогаем — стенд
  отдаёт HTML, это отдельный слой `app/web/`;
- граница из CLAUDE.md действует и здесь: в `app/services/*` не должно быть
  ни объектов aiogram, ни объектов FastAPI (`Request`, `Response`). Сервис
  принимает данные и сессию, возвращает модели.

Решение 2026-07-24 в силе: сначала натальная ветка до продукта, Матрица Судьбы
и восточный гороскоп — после.

## Следующие шаги

Ближайшая цель — **веб-стенд, на котором два разбора лежат в колонках
рядом**. Всё, что не ведёт к этому экрану, откладывается: сравнение
текстов — единственный способ увидеть, привязывается ли DeepSeek к карте
или льёт воду.

0. **`app/services/charts.py`** — СДЕЛАНО (не закоммичено). Продуктовая
   склейка: `search_places()` → `create_chart()` → запись в `charts.calc`,
   дедупликация по `input_hash`. Поиск города и создание карты — ДВА
   отдельных вызова, потому что между ними человек выбирает город
   («Ростов» — какой?). Тестов пока нет; минимум — тест на стабильность
   `_input_hash` (флаг `time_known` хеш меняет, подпись места — нет),
   он даже не требует базы.
1. **Миграция №2** ← текущий шаг. Две колонки в `charts` под веб:
   - `token` — публичный адрес карты для ссылки `/r/<token>`. По
     последовательному `id` можно подставить соседнее число и прочитать
     чужую дату и место рождения, а это персональные данные. Устроен как
     `orders.token`: 24 случайных байта, генерирует Python;
   - `person_name` (nullable) — чья это карта. Расчёту не нужно, нужно
     людям: у тестера бывает карта своя и мужа, а в админке без имени
     сравниваются «карта №3» и «карта №7».

   Правки под бота (`users.subscribed` → `default=False`, `users.sign`,
   таблица `horoscopes`) переехали в отложенный блок ниже.
2. **`app/services/users.py`** — СДЕЛАНО. `get_or_create` по паре
   `(platform, external_id)`; подписка, знак и списки рассылки отложены
   вместе с ботом. Сквозная проверка на живой базе пройдена: повторный
   вызов возвращает ту же строку и не перезаписывает `source`; тот же
   `external_id` на другой платформе даёт отдельного пользователя;
   `create_chart` поверх него считает карту, повтор тех же данных отдаёт
   ту же карту, а `time_known=False` — отдельную. Тестовые записи из базы
   удалены. Автотестов пока нет.
3. **`app/services/reports.py`** ← текущий шаг. Кеш отчётов по
   `(chart_id, type, prompt_version)`, лимит бесплатных генераций, вызов
   LLM, лог генерации. Про HTTP и Telegram не знает.
4. **`app/web/`** — стенд на Jinja2: `router.py`, `templates/`, один
   `static/style.css`. Ни сборки, ни npm, ни Vue: это инструмент для
   вычитки текстов, а не продукт.

   | Путь | Кто ходит | Что делает |
   |---|---|---|
   | `GET /` | тестер | форма: имя, дата, время, город |
   | `POST /chart` | тестер | geo → расчёт → редирект на `/r/<token>` |
   | `GET /r/{token}` | тестер | карта + текст разбора |
   | `POST /r/{token}/feedback` | тестер | оценка 1–5 + «что не так» |
   | `GET /admin` | помощница | таблица карт: имя, дата, Солнце/Асц, оценка |
   | `GET /admin/compare?ids=3,7` | помощница | тексты в колонках рядом |

   Две вещи, которые иначе всплывут в проде:
   - **LLM отвечает 30–60 секунд.** Обычная форма всё это время висит белым
     экраном, человек жмёт «обновить» и запускает вторую генерацию (то есть
     платит дважды). Лечится без JS: `POST` создаёт запись и сразу
     редиректит на `/r/<token>`, страница пишет «готовим разбор» и обновляет
     себя через `<meta http-equiv="refresh" content="5">`;
   - **оценку пишем в `events`** (`name='feedback'`, `props` JSONB) —
     таблица для этого и заведена, отдельная миграция не нужна.
5. **Выкатка стенда**: домен + Caddy (сертификат Let's Encrypt автоматом;
   на пару дней сойдёт `sslip.io`), HTTP Basic Auth на `/admin` (логин и
   пароль в `.env`), лимит генераций на cookie в сутки и общий дневной
   потолок расходов на DeepSeek. Форма в открытом интернете — это чужие
   персональные данные и наши деньги, оба пункта обязательны.
6. **Раздача тестерам и правка промптов** по живому фидбеку + пост-фильтр
   текста на собранном корпусе. Следить за фактическими ошибками (модель
   путала трин Марс–Плутон с секстилем), длиной (просим 350–500 слов,
   отдаёт больше) и тоном. Любая правка текста промпта = новая `VERSION`.
7. **`astro_core/wheel.py`** — SVG-колесо карты (kerykeion). На стенде
   уместно: картинка рядом с текстом сразу показывает, соответствует ли
   разбор карте.

### Отложено до устоявшихся промптов

**Бот** (был шагами 1–4 в прошлой редакции). Работа не пропала — она про
рассылки по знакам, то есть про старую функциональность, а не про
натальные карты:

- миграция под бота: `users.subscribed` → `default=False` (в старом боте
  подписка была явным нажатием кнопки, в наших моделях по недосмотру
  оказался `True`; рассылка без согласия собирает жалобы на спам, а по
  жалобам Telegram ограничивает ботов), `users.sign` (nullable), таблица
  `horoscopes` с ключом `(sign, period, period_key)` — это НЕ `reports`:
  `reports` привязаны к `chart_id`, то есть к человеку, а гороскоп для
  Овна один на всех;
- `app/services/horoscopes.py` — перенос `bot/services/horoscope.py` на
  Postgres, без Redis;
- пересадка бота: `main.py`, `handlers.py`, `broadcast.py` на новые
  сервисы, удаление `bot/services/llm.py`; остальные части `users.py`
  (подписка, знак, `touch_last_seen`, получатели рассылки).

**Расчёты**: `astro_core/matrix.py` (нюанс: у разных школ разная редукция
чисел >22 — сумма цифр vs вычитание 22, нужен эталонный калькулятор для

### Параллельно, не блокируя код (решение 2026-07-26)

Это не работа, а календарное ожидание — чем раньше запущено, тем лучше;
делается независимо от того, на каком шаге код:

- **Домен** (~200–400 ₽/год) — теперь не «параллельно», а на критическом
  пути: без него стенд открывается по голому IP, браузер пишет «Не
  защищено», а мы собираем дату и место рождения. Тот же домен нужен под
  ЮKassa и заявку в каталог VK, так что покупка ускоряет всё сразу.
- **ЮKassa**: самозанятость/ИП, договор, на сайте — оферта и политика
  обработки ПДн. Подключение кассы — задача на день, а вот проверка на
  стороне банка идёт неделями.
- **Заявка в каталог VK** — модерация тоже занимает недели.
- **VPS + `docker compose` (postgres + api за Caddy)** — минимум, чтобы
  стенд жил не на ноутбуке и тестеры могли открыть ссылку когда угодно.
  Бот добавится в тот же compose позже.

Отложены **VK Mini App (Vue) и пейволл** — но не веб как таковой: стенд на
Jinja2 как раз и нужен, чтобы понять, сколько будет секций, какой длины и
где проходит граница платного. Это станет ясно только на живых текстах, а
верстать настоящий фронт по неустоявшемуся контенту значит верстать дважды.
