## Что сделано

### Реализованные модули

| Файл | Что делает |
|---|---|
| `backend/astro_core/geo.py` | Офлайн-геокодинг: ~70 тыс. городов GeoNames в памяти, префиксный поиск по русским (включая исторические — «Свердловск» → Екатеринбург) и латинским именам через bisect; таймзона города из базы, для произвольных координат — timezonefinder. Возвращает всегда ИМЯ зоны IANA, смещение по дате достаёт tzdata в расчётном слое. |
| `backend/astro_core/natal.py` | Натальная карта на kerykeion 5 (`AstrologicalSubjectFactory` / `AspectsFactory` — новый API, мигрировано со старого): планеты, углы, дома Placidus, аспекты. Чистая функция `compute_natal(birth_dt, lat, lon, tz) → dict`, про geo/FastAPI/БД не знает. |
| `backend/scripts/build_cities.py` | Однократная сборка `backend/data/cities.txt` из GeoNames (cities5000 + русские имена из alternateNamesV2 по метке `isolanguage=ru`). |
| `backend/scripts/natal_cli.py` | Ручная проверка: `python scripts/natal_cli.py 1990-05-11 17:20 Касимов` печатает карту в формате astro-seek (градусы°минуты'); флаг `--json` пишет эталон для tests/golden/. |
| `backend/scripts/seek_check.py` | Автосверка с astro-seek: качает их расчёт по тем же координатам (таймзону astro-seek определяет сам — независимая проверка нашей цепочки), парсит HTML и сравнивает с `compute_natal`. Калиброван на картах, проверенных глазами. |
| `backend/tests/test_natal.py` | Золотые тесты: пересчитывают каждую карту из `tests/golden/*.json` и сравнивают (знак/дом/ретро точно, градусы с допуском 0.01°). Ловят регрессии при обновлении kerykeion/pyswisseph/tzdata. |
| `backend/app/llm/client.py` | Транспорт к DeepSeek (httpx, без SDK): один вызов `chat(system, user)`, ретрай на 429/5xx, расход токенов в `LLMResult.usage`. Модель по умолчанию `deepseek-v4-flash`; temperature 1.0 — откалибровано (1.3 разваливает текст v4-flash в бессвязицу). |
| `backend/app/llm/prompts/free_natal.py` | Промпт бесплатного разбора (`free_natal_v1`): `VERSION` для ключа кеша отчётов, стабильный `SYSTEM` (тон + запреты для модерации VK, у DeepSeek кешируется — 1024/1058 ток. из кеша на втором вызове), `build_user()` рендерит dict из `compute_natal` в компактный текст (10 самых тесных аспектов). |
| `backend/scripts/report_cli.py` | Сквозной прогон в терминале: дата + город → geo → natal → промпт → DeepSeek → текст. Флаги `--show-prompt` (без трат токенов), `--temperature`/`--model` для калибровки. |
| `backend/app/config.py` | Настройки через pydantic-settings. Описаны только реально используемые переменные (`DEEPSEEK_API_KEY`, `DATABASE_URL`, `DB_ECHO`, `APP_ENV`, `DEBUG`, `LOG_LEVEL`, `WEB_TESTER_TOKEN`, `ADMIN_USER`, `ADMIN_PASSWORD`, `VK_APP_ID`, `VK_SECURE_KEY`, `SESSION_SECRET`, `DAILY_GENERATION_LIMIT`); секреты — `SecretStr`, чтения ленивые через `get_settings()`, иначе любой импорт требует заполненного `.env` — включая pytest и alembic. У обоих секретов стенда дефолт «выключено» (`None`), а не «открыто»: забытая переменная на сервере должна закрывать дверь — без `WEB_TESTER_TOKEN` тестером не станет никто, без `ADMIN_PASSWORD` админка отдаёт 503. Тот же дефолт у ключей VK: свойство `vk_enabled` требует ОБА ключа сразу (`VK_SECURE_KEY` и `SESSION_SECRET`) — с одним подпись сойдётся, а сессию выпустить будет нечем, и человек упрётся в ошибку уже после успешного входа. `_blank_is_unset` покрывает и `VK_APP_ID`: там причина другая — пустая строка роняет валидацию на `int("")`, то есть приложение не стартует вовсе. А вот `DAILY_GENERATION_LIMIT` под `_blank_is_unset` НЕ заведён намеренно: «пусто = потолка нет» открывало бы траты на DeepSeek без предела, поэтому пустое значение роняет старт — падение заметят сразу, перерасход заметят по счёту. |
| `backend/app/main.py` | Точка входа: `create_app()` собирает FastAPI, монтирует статику стенда, отдаёт `/health` (намеренно без обращения к базе — проверка живости не должна падать вместе с Postgres). `lifespan` вместо устаревших `@app.on_event`: при старте не делаем ничего (движок базы ленивый, поэтому api поднимается раньше Postgres в docker compose), при остановке — `dispose_engine()`. Схему базы не создаём никогда, это дело Alembic. `/docs` наружу только при `DEBUG`. |
| `backend/app/logging_setup.py` | Настройка логирования, вызывается только точкой входа. Модули пишут через обычный `logging.getLogger(__name__)` — своей обёртки нет намеренно: библиотеки (httpx, SQLAlchemy, uvicorn) всё равно пишут в стандартный `logging`, и второй механизм только раздвоил бы картину. `basicConfig` без `force` даёт защиту от повторного вызова (иначе каждая строка печаталась бы дважды). httpx приглушён до WARNING — его INFO дублирует наш лог вызова LLM, но без токенов и времени; при `LOG_LEVEL=DEBUG` подробности возвращаются. Имя файла не `logging.py`, чтобы не было модуля-тёзки стандартной библиотеки. |
| `backend/app/models/` | Шесть таблиц схемы, файл на таблицу (пакет с 2026-08-22, до этого один файл на 930 строк): `users` (пара platform+external_id, is_tester, доставляемость рассылок, мягкое удаление), `charts` (локальное время рождения + tz, `calc` JSONB, `input_hash` против дублей), `reports` (ключ кеша `chart_id+type+prompt_version`, корпус: текст, модель, temperature, usage), `orders` (публичный `token` для ссылки оплаты, копейки целым числом, `provider_payment_id` UNIQUE против двойного зачисления вебхуком), `events` (воронка: name + props JSONB + ts), `posts` (очередь постов сообщества, адрес `kind+target_date+event_key+prompt_version`). Enum'ы — varchar+CHECK, не нативные PG-типы. Снаружи пакет виден как один модуль: `__init__.py` реэкспортирует классы и хранит общие соглашения, файлы ядра импортируют друг друга под `TYPE_CHECKING` — связи объявлены типами, а класс по имени находит реестр SQLAlchemy. Схема при делении сверена слепком до/после: колонки, ограничения, индексы и все восемь связей совпали. |
| `backend/astro_core/transits.py` | Календарь астрособытий из эфемерид: лунации, затмения, станции, ингрессы, точные аспекты плюс `day_sky()` — небо суток для гороскопа. Всё в московской зоне, константы знаков и планет переиспользуются из `natal.py`. Год событий считается за 1,5 с, неделя — за 0,03 с. Падежи русских названий держатся таблицей, а не морфологическим анализатором: слов ровно 22, а pymorphy3 разбирает «Рыбы» как единственное число слова «рыба». Главный урок модуля — **границу знака нельзя искать как ноль непрерывной функции**: остаток долготы по 30° в этой точке разрывается (30° → 0°), и первая версия сообщала вход Солнца в Деву 7 сентября вместо 23 августа. Планетных эфемерид в проекте нет — считаем по Moshier (0,1–0,3″ против порога золотых тестов в 1′), и флаг запрашивается явно, чтобы фолбэк не был молчаливым. 19 тестов. |
| `backend/app/llm/prompts/daily_horoscope.py`, `astro_event.py` | Промпты контента сообщества. Гороскоп — 12 знаков ОДНИМ вызовом: в одном ответе модель видит написанное предыдущим знакам и не выдаёт двенадцать вариаций «прислушайтесь к себе». Оба отвечают JSON (результат идёт и в пост, и в экран Mini App), блок правил тона скопирован из `free_natal` дословно — это условие модерации каталога VK. `MAX_TOKENS` гороскопа 3500: обрезанный JSON клиент считает браком и бросает `LLMError`, то есть день остаётся без поста при оплаченных токенах. Живьём ещё не прогонялись. |
| `backend/app/services/content.py` | Генератор контента: календарь → тексты в `posts`. Здесь же продуктовые решения — сколько постов за прогон (порог веса 40 плюс лимит 2 и подстраховка на тихую неделю), что считать одним событием (дедупликация «затмение поглощает свою лунацию»: 12.08 и 28.08 они расходятся на минуты) и как выглядит адрес поста (`event_key` с участниками, иначе в сутки помещался бы один пост). Транзакцию коммитит сам, в отличие от соседних сервисов: прогон недели это девять вызовов по минуте, и одной транзакцией восемь оплаченных текстов пропали бы из-за падения на девятом. Строки живут два месяца, чистит сам генератор. Про VK не знает ничего — публикация ручная. |
| `backend/app/llm/prompts/full_natal.py` | Промпт платного полного разбора (`full_natal_v2`, второе поколение — см. [astro-prompts-v2.md](astro-prompts-v2.md)). Ставка не на мягкость тона, а на конкретность: модель обязана называть элемент карты за каждым тезисом. Свой `TEMPERATURE = 0.8` (ниже общего 1.0: выше — теряется привязка к данным карты, ниже — канцелярит). Ответ модели — JSON по секциям, не сплошной текст: пейволл открывает первую секцию и закрывает остальные, а разрезать сплошной текст по границам смысла нельзя. `build_user()` отдаёт карту целиком (все дома, больше аспектов). Разбор ответа вынесен в `parse()` (JSON → список секций или None), а `render()` теперь надстройка над ним для терминала: показывать секции будут двое и по-разному — консоль переносит строки по своей ширине, а веб-страница обязана этого НЕ делать, жёсткие переносы на 88 колонок в браузере дают рваный текст. |
| `backend/app/db.py` | Инфраструктура Postgres без единой таблицы: `Base`, ленивые `get_engine`/`get_sessionmaker`, зависимость `get_session` (транзакцией управляет вызывающий), `dispose_engine`. Асинхронный стек SQLAlchemy 2 + asyncpg — обработчик всё равно ждёт DeepSeek десятки секунд. Заданы `expire_on_commit=False`, `pool_pre_ping=True` и соглашение об именах ограничений (обязательно **до** первой миграции). |
| `backend/app/services/charts.py` | Продуктовая склейка «данные рождения → строка в `charts`». `search_places()` (подсказки городов, синхронно, справочник в памяти) и `create_chart()` — намеренно ДВА вызова: между ними человек выбирает, какой из Ростовов его. Дубли ловятся не сравнением полей, а хешем входа (`_input_hash`, sha256; координаты округляются до 4 знаков, иначе последний бит float даёт «разные» города) плюс уникальная пара `(user_id, input_hash)` в базе. Расчёт уходит в `asyncio.to_thread`: 50–150 мс Swiss Ephemeris в event loop заморозили бы весь процесс. Вставка под `begin_nested()` (SAVEPOINT) — на гонке двух одинаковых отправок формы возвращаем ту карту, которую успел записать конкурент, вместо «current transaction is aborted». `get_chart_by_token()` — чтение карты по публичному токену для страницы `/r/<token>`, проверки владельца там нет намеренно: токен и есть ключ (24 случайных байта), а по последовательному `id` подставлялось бы соседнее число. **Тестов пока нет.** |
| `backend/app/services/users.py` | Одна функция `get_or_create()` по паре `(platform, external_id)`: веб-стенд зовёт её с `platform='web'` и UUID из cookie, бот позже — с `'tg'` и Telegram-id. Три шага: SELECT (быстрый путь, по нему идёт большинство запросов) → `INSERT … ON CONFLICT DO NOTHING RETURNING` (вставку и разрешение гонки делает сама база одной командой) → повторный SELECT, если пустой RETURNING показал, что конкурент опередил. `source` проставляется только при создании — канал привлечения это свойство первого касания. Вернувшемуся снимается `deleted_at`: строка для того и оставлена, чтобы он не упёрся в конфликт по уникальной паре. Коммита нет, транзакцией правит вызывающий. Рядом `get_by_id()` — для фоновой задачи генерации, которая работает в СВОЕЙ сессии и поэтому получает идентификатор, а не объект. |
| `backend/app/services/reports.py` | Кеш отчётов и генерация. Адрес текста — `(chart_id, type, prompt_version)`, по нему UNIQUE в базе: за один текст платим один раз, повторное открытие берёт из кеша. Реестр `_PROMPTS` связывает `ReportType` с модулем промпта (добавить Матрицу = дописать строку, не править логику); `TEMPERATURE`/`MAX_TOKENS` берутся у модуля через `getattr`, иначе общий дефолт из `client.py` — своя 0.8 сейчас у обоих промптов. Кеша в базе НЕ хватает: страница обновляет себя раз в 5 секунд, и обновление легко попадает в минуту, пока генерация идёт, а строки ещё нет, — поэтому есть внутрипроцессный замок `_generation_lock` по адресу отчёта (со счётчиком ждущих, чтобы словарь замков не тёк и чтобы замок не выбросили из-под очереди). **Замка самого по себе не хватило**: транзакцию коммитит вызывающий, уже ЗА пределами замка, поэтому между вставкой и коммитом есть окно, в котором замок свободен, а строки для чужой транзакции ещё не видно — проверка на живой базе дала одну строку и ДВА вызова DeepSeek. Поэтому `_LockEntry` хранит ещё и сам ответ модели: второй запрос берёт готовый текст и в LLM не идёт, а дальше решает база — конкурент закоммитил, значит `IntegrityError` и забираем его строку. Вставка под `begin_nested()` — тот же приём, что в `charts.py`, и он же закрывает случай второго процесса, которого замок не видит. Лимит генераций — `_LIMITS` (3 на `free_natal`), `is_tester` снимает все личные ограничения. **`_TESTERS_ONLY = {FULL_NATAL}` с 2026-08-11: полный разбор бесплатно не получает никто, кроме тестеров.** До этого дня множество было пустым, то есть платный товар отдавался всем даром — на проде так ушло 11 полных разборов при нуле тестеров. Запись `_LIMITS[FULL_NATAL] = 3` осталась недостижимой страховкой на случай, если тип откроют раньше `orders.py`; с появлением оплаты уходят обе записи, а проверкой станет оплаченный заказ. Интерфейсу доступ виден заранее через `needs_purchase(user, type)` — иначе страница выясняла бы его отказом; состав платного разбора для анонса отдаёт `section_titles(type)` (читает `SECTION_TITLES` у модуля промпта). Поверх личных лимитов — дневной потолок на весь сервис (`count_generated_last_day`, сутки скользящие: календарные обнуляются в полночь и дают всплеск трат сразу после неё). **С 2026-08-16 он считает только НЕОПЛАЧЕННЫЕ генерации**: `_check_allowed` первым делом выясняет оплату и платный разбор мимо потолка пропускает — иначе отказ приходил бы человеку, уже отдавшему 290 ₽, причём в день пикового трафика. На `is_tester` потолок по-прежнему не смотрит: личные лимиты про справедливость к одному человеку, потолок про счёт от DeepSeek, а счёту всё равно, кто потратил. Считается по строкам `reports`, то есть упавшие генерации (деньги ушли, строки нет) в счёт не идут — они редки, а след остаётся в логе как ERROR. Колонки «статус» нет намеренно: строка появляется только с готовым текстом, «нет строки = ещё готовим». **Автотестов нет**, но сквозной прогон на живой базе с заглушкой вместо DeepSeek пройден: кеш (повтор не тратит токенов), замок (два параллельных запроса → одна строка и один вызов LLM), лимит, отказ платного не тестеру, `temperature=0.8` у полного разбора, каскадное удаление отчётов вместе с пользователем. При переносе в `tests/` сценарию нужна отдельная тестовая база. ## Решения по стратегии

Обкатка идёт **сначала на веб-стенде**, потом бот, потом Mini App (решение
2026-07-27, заменяет порядок от 2026-07-25); подробности и обоснование — в
[astro-context.md](astro-context.md), раздел «Порядок выхода на платформы».
Следствия для кода, которые надо держать в голове:

- в `users` — пара `(platform, external_id)` вместо `vk_id`, плюс `is_tester`
  (тестерам открыт полный разбор без оплаты). Веб-пользователь — это
  `platform='web'` и случайный UUID в cookie: пара для того и заведена;
- **все генерации логируются** (текст, `prompt_version`, модель, temperature,
  usage) — из этого корпуса потом строится пост-фильтр текста, без которого
  на модерацию VK идти нельзя;
- веб-стенд дёргает `app/services/*` напрямую, теми же вызовами, что позже
  будет дёргать бот. `app/api/*` (JSON для Mini App) не трогаем — стенд
  отдаёт HTML, это отдельный слой `app/web/`;
- граница из CLAUDE.md действует и здесь: в `app/services/*` не должно быть
  ни объектов aiogram, ни объектов FastAPI (`Request`, `Response`). Сервис
  принимает данные и сессию, возвращает модели.

Решение 2026-07-24 в силе: сначала натальная ветка до продукта, Матрица Судьбы
и восточный гороскоп — после.

## Следующие шаги

Порядок выбран 22.08 и держится на одном доводе: **пока идёт ревью VK,
трогать нельзя ни URL приложения, ни домен**, а сообщество — единственный
выход наружу из Mini App, и проверяющий пойдёт туда. Пустая группа читается
как пункт 7 правил («непроверенные, сомнительные услуги»), и технической
защиты от этого нет.

1. **Прогнать генератор живьём.** Накатить `c7a41d6b90f2` на прод,
   сгенерировать первую пачку, вычитать глазами. До этого момента ни один
   текст `daily_horoscope`/`astro_event` не проверен на живой модели —
   промпты писались вслепую, как когда-то `free_natal`.
2. **`/admin/content`** — экран генерации и вычитки (решение 22.08,
   заменяет отказ от админки, принятый тем же днём: перевесил копипаст —
   текст поста переносится в отложку VK еженедельно, и из терминала он
   приезжает разорванным на 80 колонок). Три части: фоновый прогон недели
   с замком от двойного нажатия (`app/generation.py`), список пачки и
   тексты в `textarea` для копирования. Колонки статуса у поста
   по-прежнему нет — экран показывает и запускает, публикация остаётся
   действием человека в окне VK. CLI не делаем.
3. **Оформление сообщества руками** — обложка, описание, меню, закреп,
   фильтр комментариев. Когда в очереди появятся первые тексты.
4. **Рассылка.** Callback API (`message_allow` / `message_deny`),
   `messages.send` групповым ключом, одноразовый токен связывания
   VK-личности с веб-сессией. Список разрешивших VK через API не отдаёт —
   ведём сами, и обе ветки нужны одновременно. Письмо обязано вести
   человека на **его уже посчитанный разбор**, а не на форму ввода даты.
5. **Vue-фронт** — после вердикта модерации. Каркас (шаг 1 из
   [frontend-plan.md](frontend-plan.md)) готов и ждёт.

Отложенное с известной причиной: бот и Telegram Web App (переиспользуют
готовые сервисы, делаются после контента), `astro_core/matrix.py` (у разных
школ разная редукция чисел >22 — нужен эталонный калькулятор),
